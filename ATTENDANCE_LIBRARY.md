# Attendance and Learning Library

Implemented and applied to the connected Supabase project on 15 November 2026.

## Attendance

Owner/staff: `/owner/attendance`. Choose a batch and date to load active enrolled students. Mark individually or apply a status to the displayed search results. Statuses: present, absent, late, leave. Excel export is available.

`mark_batch_attendance` executes the existing validated attendance RPC in one transaction, with per-student idempotency keys. Invalid enrollment or status rolls back the whole request. Future dates are rejected by the existing RPC.

The attendance table is in the Supabase Realtime publication. Student/parent views subscribe to INSERT and UPDATE events, then reload their permitted records under RLS. Reconnection, browser focus and offline fallback refresh are supported. A live indicator reports subscription state.

## Learning Library

Owner: `/owner/materials`. Student: `/student?view=materials`. Parents can read their linked child's class library; teachers can read assigned active batch classes. Only the owner can publish resources, including through the older batch-material workflow.

The owner chooses a class, creates nested folders (up to 12 levels), uploads directly at the class root or inside a folder, and saves HTTPS resource links. Supported uploads: PDF, DOC and DOCX, up to 10 MB, with file-signature validation. PDFs open inside the portal; DOCX has a plain-text preview and original download. Legacy DOC requires download.

`public.library_folders` stores folder hierarchy and class. `public.library_files` stores file metadata or the HTTPS link, class, folder and creator. File bytes are in the private `learning-library` Supabase Storage bucket. Links are database records, with no duplicate Storage object.

Storage paths follow `classes/class-10/Science-<folder-id>/Chapter-One-<folder-id>/<file-id>-notes.pdf`. Non-numeric class names also include a short hash to avoid slug collisions. Storage folders appear when their first file is uploaded; empty folders remain visible in the portal through database records.

Authenticated server routes validate the actor and class/folder relationship before uploading with the server-only service role. Metadata insertion uses the actor's RLS permissions. Failed metadata writes trigger private-object cleanup. Students cannot upload library files or create folders, through either the API or direct database writes. Storage policies protect file reads by class and block direct client writes. File preview routes recheck the authenticated user's RLS access before fetching private bytes.

## Library explorer, activity and academy branding

The academy is named **Amita’s Classes**. The original supplied logo is served at `/images/academy-logo.png`, with muted red accents, blue links and neutral surfaces throughout the portal. A shared branded loading screen replaces the obsolete dashboard fallback and reads “Please wait, we are setting up your environment.” Dashboard role redirects remain functional; missing profiles have an explicit sign-out/error state.

The learning library now has a chapter/folder sidebar, a highlighted selection, breadcrumbs, a selected-folder heading and document rows. Owner upload/folder/link forms open on demand and include a full destination selector. Newly created folders open automatically. Empty duplicate legacy sections are hidden; existing older batch resources are retained in a separate section.

Migration `20261115_09_library_activity.sql` adds owner-only deletion and class-scoped `library_activity` records, generated by database triggers for resource/folder creation and deletion. The private bucket remains private. Nonempty folders cannot be deleted. File deletion removes database access first and then the private Storage object; Storage failures produce a cleanup warning rather than restoring an accessible resource.

All workspace roles receive right-side feedback for API/database mutations. The bell shows recent action feedback and class-authorized library activity. Library activity persists in Supabase and arrives through Realtime; ordinary local action feedback is kept in memory. Students see only permitted class events. Realtime activity also refreshes the explorer after deletions; client DELETE broadcasts are not used as an authorization mechanism. The notification queue for email/SMS reminders is a separate existing feature.

Apply migration 09 with `scripts/apply-library-activity-schema.mjs`. Live acceptance additionally verifies owner-only deletion, nonempty-folder protection, Storage removal, realtime delete events and event-table write/access restrictions.


## Batch library, digital checking and final submissions — 15 November 2026

See [DIGITAL_CHECKING.md](./DIGITAL_CHECKING.md) for the current implementation and limitations. Migrations 15–21 supersede older class-library selection, owner-only question-bank imports and replaceable answer submissions. Library uploads use batches; assigned teachers can import banks. Assignments have Publish/Review tabs. Assignments and tests support scanned PDF/DOCX checking with ticks, crosses, marks, pen, comments and private drafts; published checked PDFs and synchronized scores are visible to the student and linked parents. DOCX checking converts readable text, preserving the downloadable original rather than reproducing Word layout/images. Student uploads require confirmation and are final: APIs plus database triggers prevent replacement even before checking. Student subjects come from enrolled batches, pending tests show Awaiting result, and published test results refresh live. Recipient-scoped batch notifications persist across logins in Supabase, with unread badge, login toast, tab links and stored read state.
